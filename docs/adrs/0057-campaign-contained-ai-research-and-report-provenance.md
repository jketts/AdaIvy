# ADR-0057: Contain AI research inside a recorded AdaIvy campaign

- **Status:** accepted for the bounded campaign-control slice; live generated-code execution pending its OCI gate
- **Date:** 2026-08-21
- **Blueprint requirement:** Sections 6, 8, 11, 12, 15.3 and 23; ADR-0029
  central research lead; ADR-0047 bounded runtime; ADR-0054 run disclosure
- **Decision owners:** repository owner and researcher

## Context

The Graffiti 322 run exposed an architectural split. AdaIvy selected the
problem, invoked model gateways, retained verification artifacts, and rendered
the paper, but the material discovery happened in the surrounding Codex task.
That task proposed the decisive graph family, wrote and ran the search program,
selected parameters, and assembled the certificate. AdaIvy's own live Azure
route made two HTTP requests that failed with 401 and reported no token usage;
its successful internal model calls repeated an already failed route.

The resulting paper was candid in prose, but the architecture could still call
the result AI-generated by the AdaIvy project and present a manually assembled
partial spend total. Four independent gaps made that possible.

1. ADR-0047 intentionally implements only repeated proposer/verifier text
   rounds. It explicitly defers experiment scheduling and branch selection, so
   it cannot reproduce the material work the Codex task performed.
2. Static provider preflight verifies local configuration shape, not that the
   endpoint, credential, deployment, API version, and structured-output route
   work together. A passing preflight can therefore be followed by a 401.
3. No campaign boundary distinguishes an AdaIvy-originated action from an
   externally originated Codex, human, or tool artifact.
4. Publication accepts self-declared `partial` accounting and unresolved run
   identifiers. Existing runtime semantic hashes deliberately omit token and
   cost observations, but there is no separately verified operational hash.

Capturing private chain-of-thought is neither possible nor desirable. The
required property is narrower and enforceable: every material AI invocation,
declared rationale, program, tool execution, candidate selection, and verifier
result used to claim AdaIvy authorship must cross an AdaIvy boundary and appear
in a closed causal ledger.

## Decision

Add a bounded **research campaign** above the ADR-0047 runtime. It remains one
central lead and one independently reconstructed verifier; no specialist,
parallel, evolutionary, or higher search tier is activated.

### 1. The campaign is the AI work boundary

After the mandatory `before_research` novelty checkpoint, a material research
action is admissible only as one of these typed campaign actions:

- `derive`: propose a mathematical route or candidate;
- `write_program`: produce bounded source for a declared experiment;
- `run_program`: execute a previously recorded program through the experiment
  sandbox;
- `inspect_result`: interpret one or more recorded tool artifacts;
- `falsify`: propose a counterexample search or falsification step;
- `verify`: submit a selected candidate and exact supporting artifacts to the
  isolated verifier;
- `ask_user`, `suspend_branch`, or `report`: stop or hand control back without
  silently doing more work.

`plan` is reserved for AdaIvy's activation and failed/non-action model-call
bookkeeping. It is absent from the planner action schema and the model cannot
select it.

The model returns exactly one structured action per call. The orchestrator
validates and dispatches it; provider-native tool calling does not bypass the
ledger. Each action names its parent action, branch, immutable input hashes,
adapter and configuration where applicable, and a declared next-action
rationale. Unknown actions, tools, arguments, parents, or artifacts are
rejected before execution.

The useful loop is therefore explicit:

    Sol plan/code action -> AdaIvy validation -> bounded tool run
        -> recorded observation -> Sol inspect/select action
        -> isolated verifier -> recorded campaign result

This is the capability missing from ADR-0047. Merely routing its existing text
calls to Sol would not satisfy this decision.

### 2. Model-authored research code runs only through a separate sandbox port

The campaign may record model-authored Python source, but it may execute that
source only through `CampaignExperimentRunner`. The production runner must use
a digest-pinned image, no network, a read-only root, an empty noexec temporary
filesystem, no inherited credentials, a fresh work directory, bounded JSON
stdin/stdout/stderr, and hard wall, CPU, memory, process, file-count, and file-
size limits. Inputs and outputs are content-addressed. The model cannot choose a
host path, command, image, environment variable, network target, or resource
limit.

The ordinary offline suite uses a scripted runner and opens no subprocess or
socket. Live execution remains disabled until the distinct experiment image and
all enforcement probes have passed. The Phase 4B parser image is a precedent,
not authorization to reuse a parser-specific sandbox for generated code.

Tool output is an untrusted observation. It cannot create a warrant, discharge
an obligation, approve applicability, establish novelty or significance, or
enter the trusted graph by itself.

### 3. Provider activation is measured, not inferred

All live campaign model work uses the existing AdaIvy provider gateway. A shared
provider-activation service separates:

- static configuration readiness;
- endpoint connectivity;
- authentication;
- deployment/model routing; and
- strict structured-output capability.

An executed campaign performs exactly one no-retry activation request through
the same gateway, configuration, frozen environment, and pricing snapshot that
the lead will use. The activation request is the first campaign model attempt,
counts against every call/token/cost bound, and is retained whether it passes or
fails. A failed activation prevents the mathematical campaign from starting.
There is no fallback to another provider, the outer Codex task, or a scripted
gateway.

`requests_attempted`, `responses_completed`, `responses_failed`,
`responses_incomplete`, and `usage_reported_calls` are distinct counters. A 401
is one attempted request and zero completed responses; it may have unavailable
usage, but it is never reported as zero activity or as a proposer decline.

The lead and verifier configurations are separately bound and activated. Their
provider/model independence is computed from the resolved routes rather than
declared by the operator.

### 4. The campaign ledger is append-only and causally closed

The canonical campaign export contains:

- campaign, target, and content-hashed configuration identities; the required
  provider activation is the first model-call/action pair, while the novelty
  checkpoint remains the separate pre-research gate defined by ADR-0055;
- every model attempt and response status, request/response artifact hash,
  provider request id when available, usage source, pricing snapshot id/hash,
  and estimated cost;
- every action, program, tool invocation, stdout/stderr/result hash, sandbox
  profile, and terminal status;
- every imported artifact with typed origin `human`, `external_codex`, or
  `external_system`;
- every candidate selection and verifier finding; and
- the terminal action; all named bounds are bound by the configuration hash and
  enforced by the runner policy.

Each material artifact has a `caused_by_action_id`; each action's parent and
referenced artifacts resolve inside the same export. Sequence and content hashes
make deletion, insertion, swapping, and parent substitution detectable. Replay
validates closure and derives the report without invoking a model or tool.

Semantic identity may exclude execution observations, but a separate
`operational_hash` covers attempts, statuses, usage, pricing, costs, tool
outputs, and aggregate totals. Both hashes are verified. Session and campaign
rollups are recomputed from durable model-call and tool-run records; stored
rollups are never trusted by themselves.

Cost fields are named `estimated_cost_microusd` or `estimated_cost_usd`, because
the pricing-snapshot calculation is not provider billing. An actual billed-cost
field remains absent unless a separately authorized billing source supplies it.

### 5. External work is importable but cannot be relabelled

Absolute detection of thinking performed outside AdaIvy is impossible. The
enforceable rule is attribution and lineage.

An externally obtained candidate may be imported explicitly, verified, and
published. It keeps an `external_codex`, `human`, or `external_system` root,
and its accounting is `partial` or `unavailable` unless a separately verified
external usage record is included. Correctness class remains determined by the
evidence; origin does not demote valid mathematics.

`adaivy_campaign` discovery attribution is allowed only when every material
discovery root, including model and tool actions, closes inside one verified
campaign and its operational accounting is complete. A mixed or external root
must render as externally originated or externally assisted, with AdaIvy's
actual roles (for example verification, formalization, or packaging) stated
separately.

### 6. Publication derives disclosure from the campaign

A solved reader-facing report that claims AdaIvy campaign authorship must bind
the exact campaign export content hash and operational hash. Claim and
certificate run identifiers, result hashes, contributions, model calls, and
tool artifacts must resolve through that export.

The publication renderer derives authorship and run disclosure from the
verified campaign. Manuscript input cannot supply or override totals. The
reader-facing disclosure distinguishes attempts, completed, failed, and
incomplete responses; lists provider/model and pricing snapshot identities;
reports estimated cost rather than billed spend; lists executed tool/program
artifacts; and states whether causal and accounting closure is complete.

An approved AdaIvy-origin solved-result build fails closed if the campaign is
missing, partial, operationally unverified, or contains an undisclosed external
material root. A diagnostic or externally originated report may still render,
but it must say that total usage is unknown and must not print a misleading
campaign total or AdaIvy-discovery sentence.

This supersedes ADR-0054's permission to project low-level failures only in
machine evidence and ADR-0052's rule that every AI-generated claim must name
the generator literally as `AdaIvy project`. Those rules were insufficient once
the generator and the reporting system were shown to be different systems.

## Consequences

The control plane represents the class of work observed in the Graffiti 322
Codex task: Sol can propose approaches, write bounded search code, inspect exact
results, change parameters, select a candidate, and submit it for independent
checking. The activity occurs as AdaIvy campaign actions rather than as
invisible work in the host task. Live model-authored code execution is not yet a
production capability: it remains fail-closed until the separate OCI sandbox
gate named above passes.

The outer Codex task remains an operator and implementation environment. If it
does material mathematics outside the campaign, the result must be imported and
reported as external work; there is no technical mechanism that can truthfully
claim otherwise.

The trusted boundary does not move. Model proposals and experiments remain
untrusted; only existing exact, formal, and human-review paths can create their
respective warrants. Higher search tiers remain disabled.

## Acceptance gates

The acceptance suite must demonstrate all of the following offline:

1. a scripted Sol-equivalent lead writes a bounded program, the allowlisted
   runner executes it once, the exact result reaches the next lead context, a
   candidate is selected, and only the selected candidate reaches the verifier;
2. shell adapters, network requests, host paths, unknown adapters, environment
   fields, and each exceeded declared resource bound are rejected before
   execution; filesystem/process enforcement remains part of the pending OCI
   activation gate;
3. every material artifact has a resolvable causal parent, and deleting,
   reordering, swapping, or rehashing one ancestor makes replay fail;
4. failed provider authentication is a terminal recorded activation failure,
   not `proposer_declined` or `completed`, and no fallback gateway is called;
5. request attempts and completed/failed/incomplete/usage-bearing responses are
   counted independently and costs re-sum from pinned pricing records;
6. changing per-call usage, a tool result, or an aggregate total breaks the
   operational hash or aggregate verification;
7. an `external_codex` import cannot be mutated to `adaivy_campaign`, cannot
   support complete accounting, and renders external-origin wording;
8. a publication claim or certificate with an unresolved campaign/run/action/
   artifact reference is refused;
9. a closed AdaIvy campaign renders its model and tool provenance directly from
   the campaign export, with no manuscript-authored usage total; and
10. replay makes zero provider, network, subprocess, or tool calls.

Every new boundary carries a single-field falsifiability probe. `make check`
remains offline, standard-library only, and free of a container runtime.

## Explicit deferrals

- Parallel specialists, multi-agent runtime execution, evolutionary search, and
  search tiers 2--4. Subagents used to implement this repository change are not
  an AdaIvy research capability and do not activate those tiers.
- Autonomous literature discovery or acquisition beyond ADR-0050/0051.
- A general host shell or unrestricted package installation for model-authored
  code.
- Capturing or publishing private chain-of-thought.
- Treating provider usage estimates as settled billing data.

## Validation and revisit trigger

This decision remains valid while campaign closure and both hashes verify,
publication disclosure is derived rather than authored, the live provider probe
precedes research, the experiment runner retains all named controls, replay is
model/tool-free, and model/tool output grants no trust.

Revisit before widening the language or package set available to generated
programs, allowing network or credentials in the experiment sandbox, admitting
parallel workers, accepting provider-native tool calls outside the action
ledger, allowing incomplete provenance to claim AdaIvy discovery, or deriving
actual billed cost from estimated token pricing.
