# ADR-0052: Require a linked Lean artifact and contribution disclosure for every solved publication claim

- **Status:** accepted for the bounded publication-artifact slice
- **Date:** 2026-08-21
- **Blueprint requirement:** correctness contracts C9 and C15; Sections 4.18,
  9.5, 10, 15.3, and 20; ADR-0036 publication projection
- **Decision owners:** repository owner and researcher

## Context

ADR-0036 writes a file under `lean/` only when a Phase 3B attestation exists.
An exact-certificate claim can therefore render as a solved `Proposition` while
the bundle contains no Lean artifact.  The readable paper also carries author
roles, but it does not make an AI-generated result's contribution disclosure
or formal-artifact path unavoidable beside the result.

The requested policy is that every solved result automatically produces a Lean
file for formal verification, and that an AI-generated result names the
"AdaIvy project" and links to that file.  Two trust boundaries constrain the
implementation:

1. creating a `.lean` file is not the same as kernel checking it; and
2. a publication renderer cannot safely invent a prose-to-Lean translation.

## Decision

Extend each publication claim with two required records:

- `authorship`, carrying `ai_generated` and `generator`; and
- `lean_artifact`, either null or a content-hashed complete Lean source with a
  declaration name, verification status, and optional formal finding id.

A claim is a **solved publication claim** exactly when ADR-0036 computes an
evidence class other than `proposal`: `kernel_checked_theorem` or
`exact_certificate_proposition`.  Rendering refuses such a claim unless it has
one Lean artifact.  This makes the artifact requirement follow the computed
evidence class rather than a manuscript-controlled `solved` flag.

The publication bundle automatically writes every recorded artifact to
`lean/<declaration>.lean`.  Every solved claim prints a relative hyperlink to
that path and its exact status.  The status vocabulary is:

- `kernel_checked`: a recorded Phase 3B finding covers the exact source;
- `pending`: the source exists for formal verification but no passing finding
  is bound; and
- `failed`: formal checking ran and did not pass.

Only `kernel_checked` may be described as checked.  A pending file does not
promote or demote an exact certificate; it is an additional reproducibility
artifact, not its warrant.  A theorem-class claim still requires ADR-0036's
bare `kernel_checked` attestation and verified representation, and its artifact
must also be `kernel_checked` and bound to the same finding.

When `authorship.ai_generated` is true, `authorship.generator` must be exactly
`AdaIvy project`.  The paper prints the unsuppressible sentence "This result
was AI-generated by the AdaIvy project" beside that claim.  Human-authored
claims remain representable and are not falsely relabelled.

The renderer does not autoformalize prose.  "Automatically create" means that
a solved result cannot enter the publication projection without a complete
Lean-source record, and bundle generation deterministically materializes and
links that record.  The upstream research/formalization step remains
responsible for producing the source and its explicit status.

## Consequences

- A publication bundle can no longer contain a solved claim without a `.lean`
  file.
- A reader can open the exact formal artifact from the claim and can see whether
  it passed the kernel or remains pending.
- AI contribution is claim-local and mandatory where asserted; it is not
  inferred from proof status.
- Existing exact-certificate fixtures gain small Lean arithmetic certificates.
  Their publication class remains `Proposition`; generating those files does
  not turn them into theorems.
- The TeX template adds the pinned `hyperref` package and uses only renderer-
  derived relative paths.  Manuscript text never supplies a link target.
- No model, network call, new runtime dependency, warrant, applicability
  decision, semantic approval, novelty assessment, significance assessment, or
  publication approval is added.

## Acceptance gates

The acceptance suite must demonstrate that:

1. removing a Lean artifact from any solved claim is a named refusal;
2. every solved claim has exactly one emitted, hash-matching `.lean` file;
3. every solved claim's TeX contains the emitted relative link and status;
4. AI-generated claims name the AdaIvy project in the rendered paper;
5. a theorem artifact not bound to the attestation's finding is refused;
6. changing recorded Lean bytes without changing their hash is refused;
7. a pending artifact never becomes `kernel_checked_theorem`; and
8. all ADR-0036 ledger, citation, demotion, probe, and typesetting boundaries
   remain green.

## Revisit trigger

Revisit before automatically generating Lean from prose, changing the approved
import closure, treating file creation as verification, permitting a model to
set its own kernel status, accepting remote artifact URLs, or using an
unchecked artifact to grant a formal warrant.
